## Evidence classes in this package
- **CI-verified (L):** everything in the tests above, once the exact-head GitHub Actions run is read (posted on PR #8 separately).
- **Developer-reported:** local runs on Python 3.13 and 3.11 (core), the kit suite, and the benchmark numbers in `docs/WP3_6_RELIABILITY.md`.
- **CI-verified on a macOS runner (class R, from the `macos` and `macos-mlx` jobs of the CI run on the exact head, not by hand):** the Swift package builds and `swift test` passes, including the real Swift `CoreLauncher` and `CoreClient` against the real Core (start, wrong code refused, enrol, signed consent and mode calls, shutdown, restart without a code, no second owner); the Core suite passes on macOS, including `LOCAL_PEERCRED` peer checks, the Mail reader's descriptor-anchored confinement, the real `security`/Keychain, and the whole production Core as a real child process (enrol, consent, index, clean shutdown, restart on its Keychain keys, withdrawal); the isolated worker under the real `sandbox-exec` profile (TCP and UDP egress denied, file writes denied, private files — home folder, temporary folders — unreadable except the model folder, no other program runnable; **not** least privilege, see `docs/MODEL_RUNTIME.md`) and a real MLX model loading and generating inside it. It does not cover real TCC prompts, a real Apple Mail store, the SwiftUI app running (windows, Get Started, accessibility), packaging/signing, the owner's own Mac, or the speed, memory and quality of the owner's models.
- **Architect-inspected / owner-verified-on-Mac:** none yet.

## Known limitations, consolidated
1. The SwiftUI app compiles and its tests pass on a macOS runner, and its launcher and client are exercised against the real Core there, but the app has never been launched as an app; TCC prompts, signing, FileVault and power-loss behaviour are not verified.
2. Only a tiny public model has been loaded (to prove MLX loads and generates inside the sandboxed worker on a macOS runner): speed, memory, quantisation quality, real prompt-injection resistance and non-English answer quality of the owner's models are unmeasured. Claims about the model line-up remain the owner's recorded decisions, not measurements.
3. Criterion 5 now has the G-021 policy path (synthetic); no Finance or Health source adapter or owner grant flow exists yet. Criterion 7 as the plan words it (deterministic validation of numeric, date and unit claims) is met; letting the *model* call a typed tool during an answer is not built (no tools exist in this slice) and is not required by the plan's wording.
4. Consent and index status are served (owner-only, replay-protected, audited); `newest_indexed` is always null. First-run owner enrolment is served and tested with the Python client, guarded by a single-use code that only the process starting the Core knows (`docs/ENROLMENT.md`); this is **not platform-attested app identity** (still required before any public release), the launcher that starts the Core and hands the app the code is built and tested in Python with a real child process (`tests/test_launcher.py`) and in Swift, where the real `CoreLauncher` and `CoreClient` are exercised against the real Core on a macOS runner (start, enrol, shutdown, restart, relaunch after a crash, stale socket and pid file); the Mac providers a *real* Core needs (Keychain keys, Keychain anchor, folder-permission probe, Apple Mail reader, signed-manifest loading, isolated MLX engine) are tested with fakes and, for the Keychain, the production Core process and the sandboxed MLX worker, against the real thing on a macOS runner (`docs/MACOS_PROVIDERS.md`); **real TCC prompts and a real Apple Mail store have still never been touched**, the SwiftUI app has never been launched as an app, and packaging the Core into the app is not built, so the app is **not yet owner-tryable**.
5. Retrieval is lexical; Japanese and other unspaced scripts are not retrievable (recorded in the evaluation as a known gap). Search reads only items that contain a query word (term index); the index is about 5.5x larger than before.
6. The public-web egress gateway exists (`docs/EGRESS_GATEWAY.md`: https-only, public destinations only, taint-aware refusal of private content, untrusted-data results, redacted audit, one-door architecture test) and is tested with synthetic fixtures; it is **not wired into the answer flow** (that needs an API/contract extension and an architect decision), has never touched the real Internet, and a default Core makes no outbound request.
