# The macOS providers a real Core needs (partly CI-verified on a macOS runner; the rest unproven)

A real Core is built by `host.build_config` (`python -m atlas_core.serve`, started by the app's `CoreLauncher`). Every Mac-specific part is behind a seam that CI exercises with a fake. Since the CI `macos` job (GitHub-hosted `macos-latest`: macOS 26, Apple silicon, Swift 6.3, Python 3.13) the following is **CI-verified on a real macOS runner** (read from the run on the exact head, not run by hand on a personal Mac): the Swift package builds and `swift test` passes; the whole Core suite passes on macOS, including peer-credential enforcement with `LOCAL_PEERCRED`, enrolment, consent and the client over real Unix sockets, the launcher's child-process hand-off (the code is not visible in `ps -E`), and the isolated worker under the real `sandbox-exec` profile (TCP connect denied, a UDP datagram cannot be sent and a receiver sees nothing, Unix sockets and pipes work, clean environment, file writes denied, a home-folder sentinel and the temporary folders cannot be read while the model folder can, no other program can be run; the profile is allow-by-default with these denials and is **not** least privilege — see `docs/MODEL_RUNTIME.md`). Also CI-verified on the runner: the real `security` tool and Keychain (create, read, update, delete, the three store keys, the designation anchor and the task-store key provider, and the whole production Core started as a real child process that enrols, indexes, shuts down cleanly, restarts with its Keychain keys and withdraws consent), the real MLX library in the sandboxed worker, and the Swift `CoreLauncher` and `CoreClient` started and used against the real Core in `swift test`. Still **not** exercised anywhere: real TCC decisions and prompts, a real Apple Mail store, the running SwiftUI app (windows, Get Started, accessibility), packaging and signing, and the owner's own Mac and models. Nothing here reads a real mailbox, a real Keychain or a real TCC decision in CI.

| Need | Implementation | Verified how | NOT verified |
|---|---|---|---|
| A key of its own for each store (task, designation, documents index, mail index, model record) | `macos.KeychainItems.secret` over the `security` tool (value to `security -i` on standard input, never a command line) | `tests/test_macos.py` with a fake `security` (distinct 256-bit keys, created once, read back, value never in argv, failure is content-free, hostile values are base64-encoded because the real `security -i` parser is not a shell) and `tests/test_macos_native.py` against the real `security`/Keychain on a macOS runner (write, read, update, delete, restart, value not in the process list) | Keychain access prompts and item access control on the owner's Mac (a CI runner's login keychain is unlocked) |
| Rollback anchor outside the designation database | `macos.KeychainAnchor` (one JSON item); the two-phase rules are `designation.RecordAnchor`, shared with the CI fake | the same contract tests as the fake, restart persistence, an unavailable Keychain fails closed (`OSError`), a restored older database is detected; the real Keychain round trip and restart on a macOS runner | the real Keychain's behaviour under backup/restore and iCloud sync (the item must be this-device-only; not set here) |
| OS permission evidence | `macos.FolderPermissions`: can this process list the folder right now (EPERM is a refusal, a missing folder or any other error is no evidence, nothing cached) | Linux, folders and a forced `PermissionError` | real TCC behaviour (Documents, Full Disk Access for Mail), prompts and their timing |
| Apple Mail reader | `macos.EmlxMailbox` (`.emlx`: byte count, RFC 822, plist ignored); newest first, paged, every directory and the file opened relative to a pinned root descriptor with `O_NOFOLLOW` and read from that same descriptor (no name is validated then reopened; a file or parent directory swapped for a symlink fails closed), only the five stored fields, **only text/plain parts, attachments never decoded** | synthetic `.emlx` files, the mail index over it, deterministic race tests (file swapped for a symlink, parent directory replaced by a symlink, before open and before the body read; an outside sentinel is never read, identified or indexed; mutation-checked), a FIFO and an oversized file, duplicate Message-IDs, oversized and malformed files | a real Mail store (layout by version, `.partial.emlx`, `.emlxpart`, IMAP/Exchange accounts, a Mail that is open) |
| Signed model manifest installed with the app | `host.load_manifest`: signed manifest + public key next to the models; missing, altered or unsigned gives **no models**, never an unsigned one | `tests/test_macos.py` | where the key and manifest are installed (packaging) |
| Local model engine | `MlxRuntime(IsolatedEngine("mlx"))`: the isolated worker (seccomp on Linux, `sandbox-exec` on macOS, `docs/MODEL_RUNTIME.md`) | fake engines on Linux | speed/memory/quality of the owner's models (the profile and a real small MLX model under it are CI-verified on a macOS runner); gaps of the profile as stated in `docs/MODEL_RUNTIME.md` |
| Start the Core and hand the app its first-run code | `serve` + `CoreLauncher` / `launcher.CoreProcess` (`docs/ENROLMENT.md`) | `tests/test_launcher.py` with a real child process (Linux and macOS runner) | the Swift launcher at run time (it compiles), packaging the Core into the app |
| Whole Core from these parts | `tests/test_macos.py::test_a_whole_core_built_by_the_host_indexes_documents_and_apple_mail_after_consent_and_purges_on_withdrawal` | Linux, fake Keychain, synthetic folders | all of the above on a Mac |

Source type names ("documents", "mail") are passed in (`--documents-source NAME=FOLDER`, `--mail-source NAME=FOLDER`); the policy rules stay the only place they are defined. A Core with no installed manifest still starts: answers then say the local model is unavailable while the typed functions continue.
