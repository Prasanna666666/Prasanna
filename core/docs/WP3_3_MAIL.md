# WP3.3: Mail read-only BODY path — synthetic fixture evidence record

Scope: architect brief on PR #8 (comment 7069795504), `STAGE-3-EXECUTION-PLAN.md` WP3.3. Code: `src/atlas_core/mail.py`; tests: `tests/test_mail.py`. Evidence class: **CI-verified on Linux and hosted macOS, synthetic `.emlx` fixtures only**. **No real mailbox or Apple Mail store has been opened, read or copied; Mail has not been enabled on the owner's behalf; no attachment is touched.** The `macos.EmlxMailbox` reader is implemented and tested against synthetic `.emlx` files; real-store layout/behaviour and owner TCC prompts remain unverified. The Keychain provider/anchor has hosted-macOS runner evidence; owner-Mac access-control prompts remain unverified.

## What it is

```
Mailbox adapter (the platform seam)  --- guard ---> parse (strict, bounded) --> MailIndex (own encrypted file) --> Retriever / SourceStore --> the existing gate
 InMemoryMailbox (synthetic) now;                       only 5 fields taken                                            (policy -> GatedRetrieval -> ContextBuilder -> GatedModel -> verification)
 `macos.EmlxMailbox` = implemented reader; real Apple Mail store validation remains owner-enabled and unverified
```

* **Independent source type, existing gate.** The index is a `Retriever` and `SourceStore` for the unchanged `TaskService`; it names no source type in code (constructor argument). A Documents grant never implies Mail (tests with `SourceAccess` over the designation store: documents-only, mail-only, neither, both).
* **Both gates before every adapter call AND inside every write.** The index keeps only a guarded handle on the adapter: every `list_page` and every `read` first runs `SourceAccess.permitted` (owner grant AND fresh positive OS evidence, checked now); the index cannot be built without an access check. Tests count real adapter calls: nothing enabled, a missing/unknown/stale/future-dated/failing OS provider, consent withdrawn or OS permission lost at `scan:begin` and at `msg:before`, all mean zero listings or reads. A denied scan changes no state either. Access is also re-checked **inside every index write** (immediately before its transaction begins, with the index lock held), so material listed or read while permitted can never be written after a revocation: a concurrent purge either runs after the write and clears it, or the completed revocation makes the check fail and nothing is written. The slow adapter listing runs OUTSIDE the index lock, so a revocation and its purge are never blocked by it. Tests block inside `list_page`, withdraw consent (the purge completes) or lose the OS permission, release it, and prove no message row and no scan metadata are recreated and no body is read; the same between two listing pages and between a read and its write. The document index uses the same guarded write (it had the same window). Revocation purges the index; mail already in local storage is still unretrievable once access ends, even if the purge function has not run.
* **Stored fields are trusted fields; message text is not.** Sender, date and subject are the stored fields of the message record, rendered by the Core as the `headers` part (one passage per line, locator `message_part: headers`, exact span). The body is a separate `body` part (one passage per paragraph, locator `message_part: body`, exact span). Text in a body that looks like `From: ...` is only ever a body citation; claiming it is a header does not resolve (`out_of_range`). The sender and date are never parsed from the message text. These use only the frozen 1.0 `EvidenceRef` and its `message_part` locator; no contract change.
* **Honest about authenticity.** "Stored sender" means the value Mail stored for the message, which a sender controls; the Core cites it as a stored claimed field and makes no claim that it is authenticated (the `authenticity: claimed` flag remains specification-only and is not part of the currently served message evidence).
* **Strict, bounded, never repaired.** Only five fields are taken (message id, sender, date, subject, body). Missing or mistyped fields, an unparseable date, a control character (this also refuses a header line smuggled in through a sender or subject), a NUL byte, an oversized field or body, a record for another message, and an invalid identity are explicit failed outcomes with reason codes (`malformed_message`, `corrupt`, `oversized`, `unreadable`), counted in coverage; they are never searchable or cited and block `complete`.
* **Attachments do not exist for the Core.** Anything else an adapter returns (an `attachments` key, extra headers) is ignored and never stored, listed, counted or exposed (tested with a leaky adapter and a fixture that counts any attachment access: zero). There is not even a column for them. The answer discloses `attachments_not_searched` and the deferred `mail_attachment` source through the existing rule. G-O18 is a separate package.
* **Hostile content is data.** Instructions in a body (search everything, reveal secrets, send, delete, grant access to Finance/Health, change policy) change no scope, grant or state: only the granted type is searched, the question reaches the model unchanged, no grant appears or changes, and there is no action path in this module at all.
* **Never stale.** `get()` re-reads the message through the guard and re-hashes the stored text on every resolution: a changed, deleted, newly malformed or access-ended message is unresolvable and is skipped by search until rescanned and re-indexed.
* **Listing is paged and bounded; the newest messages are admitted first.** The adapter seam is `list_page(cursor, limit)` (at most `PAGE_SIZE` entries per call; a larger page is cut before anything is walked). The Core admits at most `MAX_MESSAGES` entries to a scan, the NEWEST by stored date, with a min-heap whose memory is bounded by that cap, and examines at most `MAX_LIST_WORK` entries whatever the adapter does. **There is no early stop and no reliance on the adapter's order.** A sorted prefix proves nothing about the pages not yet seen, so the Core always uses its work budget (`MAX_LIST_WORK` entries) and keeps the newest of what it saw; an adapter that lists newest first therefore gets the newest admitted, and one that breaks the order after a sorted prefix still gets a later newer message admitted. **Stated boundary of the guarantee:** entries beyond the work bound are never seen, so a newer message that appears only there is not admitted, and the scan then reports `scan_complete` false (never `complete`). A mailbox that was not fully seen or admitted is always reported that way. Tests: more than the cap in date order (the five newest admitted within a fixed budget of examined entries, never an early stop), a **sorted prefix that ends exactly at a page boundary (the cap filled by whole pages, correctly descending), followed by a newer message alone on the next page (the newer one is admitted; the test fails against the earlier order-gated early stop)**, plus the same with the newer message inside the last page, the same with the newer message beyond the work bound (not admitted, scan incomplete), deliberately out-of-date-order listings, a huge oldest-first listing (30 of 500 entries examined, 3 at a time), a page larger than asked, a mailbox that fits (complete), and newest-first indexing after a capped scan.
* **Nothing the adapter returns while listing is trusted.** A listing entry is used only if it is a `Listed` with a well-formed string identity, a non-empty string change marker and a string-or-absent date; anything else (a `None`, an integer, a float, bytes, a list, an unsupported object, an empty or over-long or ill-formed identity, a dict or tuple instead of an entry, a mistyped field) is **counted and recorded as an identity-free failed row** (`malformed_message`, synthetic identity `malformed-listing-N`): the raw value is never used in SQL or hashing and never stored (tested with a sentinel in the object's text), the scan survives, other messages are indexed, and coverage is never complete (at most `MAX_MALFORMED_ROWS` are recorded; more only keep the scan from being complete). A **page** of the wrong shape (not a `ListPage`, items not a list or tuple, a non-string cursor) ends the scan with the non-content error `malformed_listing` **before anything is written**: the previous index stands unchanged and searchable, coverage reads incomplete, and a later good scan recovers. An adapter that raises, or returns empty pages with a cursor forever, cannot corrupt the index or loop (a fixed page bound stops it); duplicate identities in a listing leave one row (the heap's tie-break never compares entries).
* **Restart-safe and bounded.** Each message's state change commits with its stored fields in one transaction; a scan is one transaction after a durable `running` marker. A six-boundary crash matrix converges to the clean-run index; re-running is idempotent and does not re-read unchanged messages; indexing is sliced, newest first by stored date, and cancellable.
* **Redaction.** Source ids are opaque; coverage carries counts and reason codes only; logs, coverage and the raw (encrypted) index file contain no sender, subject, body or identity (tested with sentinels).

## Supported scope (honest)

Message body and stored headers (sender, date, subject) as text. **Not built:** thread context, recipients/other headers, HTML/MIME parsing, attachment content or metadata (G-O18), complete real-store validation, disk-pressure pause, and any send/reply/delete/draft action (the Mail path is read-only and has no action surface).

## Known limitations and pending evidence (not claimed)

* No real mailbox or Apple Mail store has been exercised; the implemented reader (`macos.EmlxMailbox`) has been exercised on synthetic `.emlx` files on Linux and a macOS runner, but real-store message identity/versioning, scale and performance are unverified. The reader reads the byte-count line and headers to list a message and, to read one, walks the MIME structure in order and stops exactly after the delimiter line that ends the first text/plain part (one byte per read, no read-ahead): no attachment byte is read; a message with a non-text payload before the text is unreadable.
* Coverage was not carried in the answer envelope at the WP3.3 implementation snapshot; WP3.4 subsequently added it to served API 1.1 answers. Ranking is lexical term overlap.
* Listing bounds assume only that the adapter honours `limit` and the cursor; an adapter that never ends its cursor is stopped by the work bound, and one that ignores the limit is cut to it. Whether a real Apple Mail adapter can page newest-first efficiently is unverified (Mac-pending).
* The listing change-marker is adapter-supplied and only an optimisation: correctness never depends on it (every read is re-hashed).
* Mac-pending: TCC/Mail automation permission, the Keychain anchor and store key provider on the owner's Mac (the real `security` tool is exercised on a macOS runner), real-volume behaviour, performance, owner-authorised end-to-end validation (which needs explicit owner enablement).
