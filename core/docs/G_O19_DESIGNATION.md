## What it is

```
owner decision (OnboardingDecision)                          OS permission (OSPermissionProvider: FakeOSPermissions in CI)
        |                                                                         |
DesignationStore (own encrypted file: grants, state, hash-chained audit)          |
        |  grants_for()                                                           |
        +------------------------------ SourceAccess ----------------------------+     one GrantSource for the existing PolicyEngine
                                              |  permitted()
                  DocumentIndex.scan / run / search / get  (and every future source adapter)
```

* **Policy stays the single decision point.** `SourceAccess` is just a `GrantSource`: `PolicyEngine` still judges grant, purpose, ceiling, expiry, restricted and deferred types, and mints the token with the same grant-identity and ceiling binding (incl. the checkpoint binding from `bd62fc1`). There is no second permission system.
* **Lifecycle per source type:** not_configured -> enabled | declined; declined -> enabled; enabled -> revoked; revoked -> enabled with a NEW grant identity. Nothing is enabled by default; documents and mail are decided independently; there is no per-folder grant and the store never records a folder name. Designable types are those the rules know that are not restricted and not deferred (today: `documents`, `mail`; never `mail_attachment`, Finance or Health).
* **One Get Started decision:** `OnboardingDecision(enable, decline, expires_at)`, also buildable from the 1.1 `ConsentRequest` shape. A decision is validated whole and applied in one transaction; a refused decision changes nothing. A request id is single-use (replay protection): an old enable cannot be replayed after a withdrawal.
* **Grants** are the existing `SourceGrant` (valid against frozen 1.0): unique opaque id, ceiling = the policy's own sensitivity for the type (never above), purpose `answer_question`, optional expiry. An expired grant is revoked (and purged) by a sweep.
* **Durable and verified.** One new encrypted file; every change commits together with a content-free, hash-chained audit row (types, states, grant id, reason code). Before anything is trusted the record is re-verified: chain, head (detects rolled-back rows), states vs audit, each grant's digest and revoked flag, schema version. Any mismatch (`corrupt`, `downgraded`, tampered, unreadable) makes every grant disappear and every change refuse (`StoreCorrupt`): fail closed.
* **Rollback anchor (outside the database), two-phase.** A database restored from an older complete copy brings back matching rows, chain, head and state, so in-database checks cannot see it. The store therefore requires a `RollbackAnchor` (no default) kept outside the database, and every change is written in two phases: `prepare` records the intended (sequence, head) in the anchor BEFORE the database commits (if the anchor cannot record it, the change is not made), and `commit` records it as finished AFTER (if that cannot be recorded, **nothing is trusted**: `grants_for` returns no grant and every change is refused until the anchor is reconciled). At every verification the database must match the anchor exactly: an older database (a restored snapshot, even one that loses only the last change), a used store with no anchor, a fork, an anchor that cannot be read, a database holding a change the anchor never recorded, or a pending record that matches neither state all fail closed. There is no state in which the database is accepted ahead of what the anchor has recorded.
* **Crash and restore windows are closed by recorded intent.** If the anchor holds a pending change that the database lacks (the process died before the commit, or an older snapshot was restored over a database whose commit the anchor never finished), the pending record decides: a **restriction** (owner withdrawal, expiry, loss of the OS permission) is **applied now** to the database and then recorded, so a withdrawal can never be undone by a crash or by restoring an older snapshot; an ordinary change (an enable, a decline) is **dropped**, so nothing is ever granted by a change that did not commit. A pending change the database already has is finalised. A new, empty store under an older anchor is refused until the owner calls `reset_anchor()`, which works only on an empty store. **In CI the anchor is `InMemoryAnchor`, a deterministic fake that models this contract. The real platform secure-storage (Keychain) anchor is NOT implemented or verified here (Mac-pending, WP3.6); the design is rollback-resistant only relative to the integrity of that anchor, and full rollback detection is NOT claimed until the platform implementation is verified.** An attacker who also controls the anchor can append legal-looking events (for example a `purge_completed`) that the chain rules accept; that is outside what this design detects (a deleted anchor on a used store is refused, but a forged one is not distinguishable). The anchor is read at every verification; its real cost is unmeasured.
* **OS permission is evidence, not a flag.** `OSPermissionProvider.current(type)` must return fresh (<= 30 s, not future-dated), positive evidence for exactly that type; a provider error, stale or wrong-type evidence is "unknown" and denies that check. Consent alone, a cached boolean, a UI checkbox or an environment variable is never accepted. A permission that was once evidenced and is then positively reported missing is a **revocation** (grant revoked, derived data purged; a new grant needed later); "unknown" never revokes.
* **Everything is gated, at the actual open.** `DocumentIndex` requires an `AccessCheck` (no default; `AllowAll` is test-only) and hands the scanner a guard it cannot be built without. The guard runs immediately before EVERY directory open, every listing and every file open, after any pre-read hook, so access ending at any boundary (including between two components of a path, or at the `doc:before` hook) means zero further opens. Search (raises `PermissionRevoked`) and `get()` (returns nothing) also touch no stored text unless the owner grant and the OS evidence are both current (matrix over consent × OS state, and open-counting tests with consent withdrawn or the OS permission lost at each boundary). Model-context construction and the model door are gated by the unchanged `ContextBuilder` / `GatedModel` re-validation through the same policy.
* **Everything security-relevant is in the audited, anchored record (no loose flags).** Two facts used to be mutable columns outside the hash chain and the anchor; both are now audited events that go through the same two-phase anchored transaction, so an older database cannot silently flip them. (1) *The platform permission was observed for this grant* is the audit event `os_permission_seen` (once per grant): a later positive loss is a revocation only if that event is in the chain, and restoring a snapshot from before it (or before the loss) is a rollback against the anchor. (2) *The purge of a revoked grant's derived data is complete* is the audit event `purge_completed`: "purge owed" is derived from the chain (a revoked grant without that event), never read from a flag. The chain itself is checked for LEGAL steps (an observation only for the enabled grant and only once; a purge completion only for a revoked grant and only once; a new grant only from a state whose old grant's purge is recorded; a revocation only of the enabled grant), so even a correctly hashed forged event is refused. Running a purge is not the same as recording it: a purge whose completion cannot be recorded (or whose process died first) stays owed, blocks a new grant (`PurgePending`) and is simply run again.
* **A withdrawal is one transaction.** Consuming the request id, revoking the grant, the audit row and the durable purge marker commit together (a crash before the commit leaves the source enabled and the request id unused, so the same withdrawal can be retried; a crash after it leaves a whole withdrawal with the purge still owed). The purge runs only after that commit.
* **Revocation purges.** `register_purge(type, fn)` registers the function that deletes derived data (the document index registers `purge`); it runs after the revocation commits. A purge that fails or never ran leaves a durable `purge_pending`: the source stays revoked, a new grant for that type is refused (`PurgePending`), and `run_pending_purges()` finishes it at the next start.
* **Owner-facing state at this snapshot** (not yet served at WP3.3): `SourceAccess.consent_state()` returns the 1.1 `ConsentState` shape. It is subsequently served through the owner-only API 1.1 consent routes.

## Boundaries and limitations (honest)

* **Historical WP3.3 boundary:** no API 1.1 route was served at this package snapshot. Later WP3.4 added `/v1/consent`, `/v1/consent/{grant_id}` and `/v1/index/status`, with signed owner-only enforcement and replay protection; see `CONTRACT_1_1.md` and `STAGE3_ACCEPTANCE.md`.
* `request_id` single-use gives replay protection for these calls; it is not client authentication.
* `FakeOSPermissions` is a deterministic CI stand-in. **macOS TCC / Full Disk Access discovery, the real Get Started UI, and FileVault behaviour are not implemented or verified.**
* The Keychain key provider for this store (real data) is WP3.6; tests pass a test-only key.
* Expiry is revoked by a sweep on use, so a denial caused by expiry reports `grant_revoked` (the closed reason enumeration is unchanged) and the audit row says `grant_expired`.
