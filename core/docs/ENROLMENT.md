# Owner enrolment (first run) and client roles

Requirement: only an enrolled, authenticated owner client may change settings and source grants (TARGET_ARCHITECTURE.md; HANDOVER.md). The Core, not the UI, decides (signed request, fresh, single-use nonce, audited change). This page records the first-run enrolment flow. The Python Core path is tested on Linux; `CoreLauncher` and `CoreClient` are exercised against the real Core by `app/Tests/AtlasKitTests/EndToEndTests.swift` in the hosted macOS CI job. The exact-head workflow result must be checked before claiming that job passed. The app's KeyStore/Get Started UI still needs owner-side walkthrough; this is not proof of owner-Mac TCC or human UX acceptance.

## Flow
1. The app creates a random client id and an Ed25519 key (Keychain on a Mac) and keeps the private key there. Nothing secret is ever sent.
2. First run, while the Core has **no owner client**: `POST /v1/enrol` (API 1.1 only) with `{client_id, public_key (32 raw bytes, base64), role: "owner", bootstrap_code}` is accepted **unsigned**, once, **only with the right one-time code**. The code is generated by the process that starts the Core, handed to the Core and to the app over a private channel (for example an inherited pipe, never a file or the environment), compared in constant time as a hash, never logged or stored, locked after 5 wrong tries until restart and used up by the first success. **The app owns its Core**: `CoreLauncher` (Swift, exercised by the hosted-macOS end-to-end test) / `launcher.CoreProcess` (Python, tested with a real child process) starts `python -m atlas_core.serve`, generates the code and writes it to the child's standard input, a pipe only the two hold: never argv, environment, a file or a log (`tests/test_launcher.py` checks, on Linux, `/proc/<pid>/cmdline`, `/proc/<pid>/environ`, every file in the data folder and `ps` output). **A Core with no owner and no code refuses to start** (a `open_bootstrap` development flag exists for tests only). It still arrives over the Core's owner-only Unix socket (folder 0700, socket 0600, peer user id checked by the transport), so only a process of the owner's own account can reach it. The check and the write are one step under one lock: of any number of racing callers exactly one becomes the owner client.
3. From then on the window is closed for good (also after a restart: the registry is persisted, mode 0600, public keys only). A second unsigned enrolment gets `unauthenticated`.
4. An enrolled owner client may enrol further clients with a **signed** `POST /v1/enrol`, only as `member` (it can ask questions and read index counts; it cannot read or change consent, and cannot enrol anyone). An owner client cannot mint another owner client. A taken id is `conflict`.
5. Consent routes remain owner-only (`/v1/consent`, `/v1/consent/{grant_id}`); the signed request's nonce is the single-use request id of every consent change.

## Threat model and limits
- What this stops: another user account, a remote host, a browser page or any non-owner process without the socket; a second enrolment racing or following the first; a member escalating; a key changing silently (re-enrolment of an existing id is refused).
- Also stops: **another process of the same user that merely reaches the socket** (without the code it cannot enrol, and it cannot guess: 5 tries then the gate shuts). This was the architect's first-owner takeover finding; the owner delegated the choice and I chose this step.
- What it does not stop: a process that can read the launcher's or the app's memory or the private channel, i.e. one that has effectively compromised the account. **This is not platform-attested app identity**: the Core still does not prove the caller is the signed Atlas app. That (a code-signing requirement checked on the peer) is a Mac packaging item (G-O12), **not built**, and remains required before any public release. The Swift `CoreLauncher`/`CoreClient` process path is covered by the hosted macOS end-to-end test; the owner-facing KeyStore identity/Get Started flow and human permission walkthrough remain separate owner-Mac gates.
- Revocation: a revoked client is refused everywhere (`forbidden`); re-opening the first-run window after revoking the only owner is **not** implemented (the owner would need to reset the data folder); recorded as a limitation.
- iOS and remote devices: Stage 8 (G-O14/G-O15). Nothing here is remote enrolment.
