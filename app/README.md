# Atlas macOS app (SwiftUI) — builds, is tested and is launched in hosted macOS CI; no person has walked through the UI

**Status: CI-verified to build and to pass `swift test` on a GitHub-hosted macOS runner (the `macos` job); launched in hosted CI by the `app` job (it starts its Core and the Core stops with it) but not used by a person, so nothing about how it looks or reads, or its accessibility, is verified. The real Swift `CoreLauncher` and `CoreClient` are exercised against the real Core in `swift test` (`Tests/AtlasKitTests/EndToEndTests.swift`).** The first compile on the runner found and fixed three real Swift errors (the Unix socket address code, a `@State` declaration, and a `self` capture before init); a Linux container cannot compile Swift. The packaged app target has been launched in hosted CI, but no person has walked through its window, Keychain access, Get Started flow or accessibility behaviour.

What it is: a Swift package with `AtlasKit` (signing, catalogue, Unix-socket HTTP client, view models) and `AtlasApp` (Get Started, conversation, progress, cancel, citations with "show the source passage", model line, coverage and notices). It speaks the same signed API 1.1 as the verified Python reference client (`core/client/atlas_client.py`) and reads the same `ux_catalogue.json` (copy of `core/client/ux_catalogue.json`; keep in sync).

## On a Mac
1. `cd app && swift build && swift test`. The tests pin the signing message to the known-answer vectors in `core/docs/CONTRACT_1_1.md`; if they pass, the Swift signing equals the Core's.
2. Start a Core (the composition root is `core/src/atlas_core/app.py`). On first run the app creates a random client id and an Ed25519 key in the Keychain (`KeyStore`) and enrols the public key as the **owner** client (`POST /v1/enrol`, unsigned, accepted once while no owner client exists, over the owner-only socket; `core/docs/ENROLMENT.md`). The app now starts its own Core with `CoreLauncher` (a child process; the one-time code goes over the child's standard input, never argv, environment, a file or a log); the Python launcher (`core/src/atlas_core/launcher.py`) does the same and is tested with a real child process; the Swift `CoreLauncher`/`CoreClient` are also exercised against the real Core by `EndToEndTests.swift` on the hosted macOS runner. Packaging the Python Core into a self-contained app, owner TCC/Mail access and target-Mac validation remain unverified.
3. `swift run AtlasApp`. Walk the owner acceptance brief in `core/docs/STAGE3_HANDOVER.md`.

## Consent and lifecycle (review 6013382016)
- **Get Started is opt-in.** Every source starts off; "Continue" is always available (with nothing selected it reads "Continue without enabling anything", makes no request to the Core, creates no grant, and is remembered). The logic is `GetStartedChoice`/`GetStartedFlow` in AtlasKit, covered by `GetStartedTests` (no selection, one source, both, and "not shown again after an empty choice").
- **The app owns its Core.** Quitting the app (delegate `applicationWillTerminate`, last window closed) stops the Core, waits for it and reaps it. `CoreLauncher.start` is idempotent and first reaps a Core a previous instance left behind (pid file next to the socket, only if that pid is really `atlas_core.serve`; an unrelated pid is never touched) and a stale socket. If the app crashes instead, the Core stops by itself within a second (it watches its parent). Covered by `EndToEndTests` (stop/reap, duplicate start, relaunch after a crash, stale socket and pid file) on the macOS runner and by `tests/test_launcher.py` (parent killed → Core exits; mutation-checked). The quit path itself (a real app being quit) has not been exercised.
