# Standing decisions (from the owner)

Every change is checked against this list before it is called done. It records what the owner has already said, so it is never asked twice.
If something here is wrong, the owner says so once and it is changed here.

## The product
- One personal platform called **Atlas**, one address (`http://atlas.localhost:8000`), one look. Today it holds **Finance** and **Documents** (files, mail and pictures in one); **health, travel, documents and more** are coming. No codenames on screen (not Finance, not Lumo, not Aperture).
- It is **one app**. Behind the one address its parts (money, documents and mail, pictures, later health and travel) keep their own storage and tools, but **every part's data is available to the one assistant and is used based on the question**: it can chain tools across parts inside one answer (ticket dates, then spending on those days, then the pictures taken on them). Parts do not talk to each other behind the scenes; the assistant is where they meet.
- **One chatbot for everything (one assistant over all data, using every part's tools)**, a general assistant the owner can simply talk to, which can also find information, browse, filter and find what things have in common, and give pictures or documents **only when asked**. No per-app chat buttons.
- **One button to read everything new** (documents, pictures, anything). Each kind of data is read in the way that suits it: photos get the extremely detailed indexing and stay on the external drive; PDFs and other documents keep their own reading and live on the Mac.
- **One document reader for everything, a common service (`library/`, shown as Documents), not part of Finance:** every file and mail is read once; the model says what it is (invoice, ticket, booking, medical, insurance, tax ...), code verifies amounts and dates, and any app asks for the kinds it needs (`/api/documents?kind=`). Bank statements are still imported only from the finance folder.
- **One document processor** in the end: whatever arrives goes through one intake and is handed to the right module, which verifies it.
- **One AI model**, one address, for input and output. Cross-queries must work ("expenses, pictures, health reports and tickets for my India trip 2026").

## How much AI, and where
- **AI is for understanding, routing, semantic search and explanation. The model decides what a message means, which part it is about and what to show. Do not decide that with word lists or regular expressions**, not even as a fallback.
- **Code, SQL and specialised tools do the actual work**: every figure, filter, date and total; EXIF, CLIP, faces and OCR for photos.
- **Agents and RAG wherever they are the right tool** (open questions, several steps, documents and notes). Retrieval only for unstructured text, never for the ledger.
- **Chat questions and answers are fully AI.** The model understands every message, routes it, calls the tools and writes the answer. No question is answered by code alone, and no word list or keyword rule routes or answers (when the model is not running the app says so). Code still does all the arithmetic inside the tools and checks every figure in an answer against the data before it is shown.
- Understanding runs on measured evidence: `python -m atlas.evaluate` scores the model by difficulty level and times each path; run it on the owner's Mac after any change to prompts or models.
- The AI never modifies or deletes source data on its own. **Moving, deleting and exporting pictures is a feature the owner wants**: it goes through one gate in Documents (the assistant can only prepare and describe it; a confirmation window shows the full list and only the person pressing Confirm there carries it out, after every check is run again; every move is journaled, audited and undoable, and a delete is a move to a trash folder, never an erase. The same gate **files original documents into folders of the inbox** (moved, undoable) and **copies mail messages** into `Filed mail/<folder>` (the mail stays); bank statements and Apple Mail's own store are never written to (the app sees the inbox **read-only by default**; filing is off until Documents is started with `LIBRARY_INBOX_MODE=rw`). Trip albums are one such change (`Trips/<year> <place>`).
- **Everything offline.** The apps never connect to the internet or a mail server. The only online steps are ones the owner runs outside the apps (downloading the model once, the exchange-rate file, building the Docker images, and Apple Mail's own syncing). Email is read from local files: Apple Mail export, `.mbox` or `.emlx`; there is no live mail fetch unless the owner decides otherwise.
- **Mail is read by the same Update button** (Apple Mail's folder, read-only, in the sealed reader), and **what is found in mail and documents feeds the calculations** (bills due, invoice-against-bank, tax, insurance, trips), not only search. A cheap gate picks what is worth the model's time; code verifies every amount and date.
- Never connect to the cloud. Everything runs on the owner's machine. (The old optional cloud reader in Photos has been removed entirely.)

## Numbers and honesty
- **Numbers must be exactly right.** Business-critical. No excuses. A figure that cannot be proven is not shown as fact; say plainly what could not be proven.
- Do not hard-code bank formats: the model infers the layout, code reads the figures, balances prove them. A file that fails its proof is left out and flagged.
- No CSV files made for the owner. No manual add or edit for event grouping. Original currency by default.
- No "Proven" badge; make sure it is right instead.
- Reports say what was verified and what was not, with no overclaiming. Nothing has been run on the owner's real data or Mac unless stated.
- The assistant (Claude) never accesses the owner's finance data and never asks for it to be pasted; the owner reports counts and words only.

## The interface
- Few words. Simple, non-technical language. Easy terms.
- Modern, attractive, easy to find things in; the same design in every module with its own colours. Charts and cards, not walls of text.
- Monthly or one-time expenses, never "everyday".
- The latest month with data is the default view (statements arrive monthly).
- Pictures and documents appear **only when asked for** (a count or a question is answered in words).

## Security and operation
- Secure by design for sensitive personal data; structured, fast, reliable; strict, modern coding standards enforced by tests and CI (complexity limit, strict types, lint, formatting, architecture tests).
- Threat model: **theft or loss of the laptop is out of scope.** No login password, no FileVault requirement. Other programs and web pages reaching local ports, hostile files, prompt injection, leaks and bugs **are** in scope.
- Health data is locked until unlocked each session (default; change by decision).
- **Very personal data (mail, documents, statements) is kept only in the encrypted database.** The sealed reader's readable copy is deleted as soon as the app has stored it; only content-free markers remain. Nothing personal goes to logs, the network or git.
- **Calls between the platform's programs are signed** with a shared secret kept in the Keychain (`scripts/platform-key.sh`); a service refuses unsigned requests. Opening an app's port directly in a browser therefore no longer works: use Atlas.
- Docker by default for both apps; no internet for the apps; originals mounted read-only, (the inbox can be made writable with `LIBRARY_INBOX_MODE=rw`, and then only the confirmation window writes to it).
- A **weekly summary** (what changed, what is due, what needs a check) is two tools, `weekly_summary` (Finance) and `whats_new` (Documents); the one assistant composes it from them. No figure is written by code into prose.
- **Names:** the three parts are Atlas, Finance and Documents; nothing says Orbit any more. What held your data was renamed *safely*: the data folder `~/.orbit` → `~/.atlas` and `orbit.db` → `finance.db` are renamed once on first start; `~/OrbitInbox`/`~/OrbitFinance` → `~/AtlasInbox`/`~/AtlasFinance` (the old names stay as links); the Keychain key is **copied** to `finance-db-key` (the old entry is kept); the Docker volume `orbit_orbit-data` is **copied** to `finance_finance-data` (the old one is kept until the owner deletes it). Settings are now `ATLAS_*`.

## How to work with the owner
- Do not make the owner explain things again. Check this list and `docs/architecture.md` first.
- Do the work; report briefly and honestly: what changed, what was verified, what was not.
- Ask only when a decision truly belongs to the owner.

- **What the person sees:** Documents has three sections of the same store: **Documents** (files), **Emails** (mail) and **Pictures**, plus Trips, Places, People and Changes. Finance is the money views and calculations over those documents, not a second reader. While reading, progress shows only a number done so far (no total, because files may still arrive); Finance shows "Waiting for Documents" until Documents is done.
- **Menu and Update, as the owner set them:** the menu is Documents, Mails, Pictures, Travel and Finance (Health when its lock exists); the first four are views of the one reader, Finance is the money app. **The Update shows what was added, in three rows: Documents, Pictures, Mails, each with its full number** (the reader counts what is in its folders at the start of every round; "N of M" while reading). Finance speaks up only when something needs a check.
- **Starts by itself:** `scripts/install-autostart.sh` installs a login item (LaunchAgent) that starts Docker, Ollama and Atlas at every login and an `Atlas` app that opens the address. Containers keep `restart: unless-stopped`.
- **Speed and safety, measured (60,000 documents, 50,000 photos):** the search re-indexes only what changed and skips even the check when nothing did (first index 2.8 s instead of over 100 s; each later question about 0.1 s); counts, kinds and the Update numbers come from indexed columns and are reused for 3 s; whole-library photo pages are worked out once per change to the library; the model stays loaded 10 minutes in every part. Services started in Docker refuse every request when the platform key is missing (`ATLAS_REQUIRE_SIGNATURE=1`, and the compose files will not start without it); unlocked Health closes again after 15 minutes unused; every container has memory, process and CPU limits.
- **Reading never hangs the computer:** nothing is read until the person presses **Read new files** (starting the computer or the apps starts no big read); the reader runs at low priority, two files at a time, with a short rest after every batch and after every model call; the person can **Pause**, **Resume** or **Stop** at any time (it waits or ends at the next safe point, nothing read is lost, and the next press carries on). The button is called "Read new files" because it reads files, mail and photos.
- **Savings rate, defined:** saved = money in − what was really spent. Money put into investments is saved, not spent (and shown as `invested`; `kept_in_accounts` is what stayed in the accounts). A refund or reimbursement linked to a trip comes off what was spent. Goals and the forecast keep counting money that left the accounts. `check_totals` shows what the figures are made of (months without a statement per account, category sums, what was left out as transfers or refunds) so a wrong total can be traced without anyone sending their figures.
- **Health and Travel are built in Documents and shown by Atlas as their own apps.** Health (locked every start, closes after 15 idle minutes): timeline, lab values over time and medicines, copied from the documents exactly as printed. The model quotes values and medicines and code keeps only what the document itself prints (test name, result, unit, range, dates); nothing is interpreted, judged or advised. Travel: trips from tickets and bookings (and photo-only trips), a trip page with the tickets, references and amounts as printed (booked totals added up exactly per currency), other documents of those days and the photos, upcoming trips, and a calendar file. What a whole trip cost is asked of the assistant, which adds up the real payments in Finance.
- **Trips have a packing list:** the person's own checklist per trip (tick, add, remove), started on request from a standard list whose quantities are plain arithmetic on the number of days (capped, because on a long trip you wash). It is app data, not a change to any file. Expenses of a trip stay in Finance (the trip page asks the assistant); photos on the trip page are left as they are.
- **Health lab values (summary and flags):** the common tests (hemoglobin, HbA1c, glucose, cholesterol, LDL, HDL, triglycerides, creatinine, eGFR, TSH, vitamin D and B12, ferritin, CRP, liver values, sodium, potassium, blood counts) are grouped under their common names whatever the report calls them (English or Dutch). The page opens with a summary: how many results lie outside the reference range **printed on that report**, or that none do. Each test shows its latest result, whether it is inside or outside the printed range, and the exact change since the reading before. A flag is only a comparison with the printed range: Atlas never says what a result means, diagnoses or advises. Results with no readable range carry no flag.
- **A light start (8 GB Mac):** nothing loads the model when the computer or the apps start (the first question does); the model leaves memory 2 minutes after the last question (`ATLAS_MODEL_KEEP=10m` and `ATLAS_WARM_MODEL=1` for a bigger Mac); Documents builds its search index two minutes after it starts; the login script waits 45 seconds, runs at low priority, starts Docker and Ollama only if they are not running and never rebuilds (`ATLAS_NO_BUILD=1`). The containers restart with Docker by themselves.
- **Folders by category, and iCloud in place:** the reader gets a folder per category (`~/AtlasFinance`, `~/AtlasHealth`, `~/AtlasTravel`, and `~/AtlasInbox` for everything else) and any extra folder listed in `~/AtlasFolders.txt` (`category=/path`, for example one in iCloud Drive), all mounted **read-only**, so originals stay where they are and cannot be changed. A document in a health folder is a health document whatever the model says (locked like the rest). iCloud files that are only in the cloud must be downloaded first, and Docker needs Full Disk Access for such a folder once.
- **Read new files picks up the latest versions:** every press reads new and changed files from every folder (iCloud ones included). A changed file replaces its older version in the store (one file, one document), and going back to earlier content reads it again. Only the stored text is replaced: originals are never touched, and what Finance already imported from an older statement stays (its payments are matched by their own reference, so nothing counts twice). A file that was deleted from a folder is not removed from the store, because a folder that is only temporarily missing (a drive not connected) must never empty it.
- **Stop reaches everything that runs:** counting and walking the folders, taking in the reader's output, the model's reading, the search-index build (partly built stays, nothing is forgotten) and the picture part of a read. Empty default folders (`~/AtlasHealth`, `~/AtlasTravel`) are made and read only when the person has no folder of that kind or has put files in them.
- **Big mailboxes do not exhaust memory, and a busy service is not an off one:** documents are judged a hundred at a time (the full text of tens of thousands of mails never sits in memory together; before, the reading service ran out of memory, was restarted and lost its place, which looked like it switching itself off). Atlas reports an app that does not answer in time as busy, keeping what it last said, and shows "switched off" only after two missed looks in a row; a refused connection is really off.
- **Status answers never wait on the database:** the numbers shown while reading are given at once from the last answer and brought up to date in the background (one refresh at a time, on its own connection), so a big read that keeps the database busy cannot make Atlas time out and show the service as off.
- **Rebuilds after a code change take seconds:** the images install their dependencies (PyTorch, the picture and document libraries) in layers *before* the code is copied, and the packages themselves with `--no-deps` after it. A test keeps the dependency list in `library/Dockerfile` equal to the one in the project files.

## No file type is turned away; counting never blocks reading
- What a file is gets judged from its contents (`sniff.py`), not from a list of extensions. Unknown formats keep their readable words, or just their name. The reading panel and the `unread_files` tool say what was not read and why (iCloud-only, alias, too large).
- Counting all files (big mailbox, iCloud) runs alongside reading, so reading starts at once and totals appear when ready. Before, the panel sat at the start until the count finished.

## One scanned PDF never holds up the reading
- Scans are read with OCR; a file that needs more than 2 minutes keeps the pages read so far (`ocr_cut_short`) instead of being dropped after 5. Seen on a real run: several scanned PDFs each timed out at 300 s with two readers, so the count sat still.
- Second-opinion PDF engines (pdfplumber, poppler) only run for PDFs up to 60 pages and for at most 60 s each. A real run showed a 300 s timeout on a long lecture-notes PDF with a normal text layer: the extra engines were the slow part, not OCR.
- Reading and judging no longer take turns for hours: one Update round judges at most 20 documents (`JUDGE_PER_ROUND`), then takes in what the reader produced meanwhile. Before, the model worked through every waiting document (tens of thousands of mails) in one go, so the file count rose once per press and then stood still.

What an email says (its kept facts) still feeds trips, Finance and the calendar. The search index carries each hit's document key (`ref`), so a hit opens the right document whatever it is called.

## "No table was found" (owner's report: 73 statements not read)
- Cause found: file types were sniffed from the first four bytes (`%PDF`), so a PDF with a newline or byte-order mark before its header was taken for text and lost its positioned table. The header is now looked for in the first 1,024 bytes (as the PDF format allows), and those files are read again (their older version is replaced).
- The statement reader no longer insists on a positioned table: with none, the printed lines are split where the gaps are wide and the same layout question and the same proofs (running balances, opening + payments = closing) decide whether any figure is trusted. A file that still has nothing says why (a scan, a protected file, plain paragraphs).

## How to know the reader works on your files: a check you can run
- `library-parser --check [N]` reads every file in the inbox and the category folders (or an even sample of N) the way the reader reads them, stores nothing, and prints counts by what each file is (PDF, text, sheet, image, binary ...) and how reading went (text, text with a table, scan, no text, failed with the reason), with three file names per problem class so you can look at them. Run it in the parser container: `docker exec atlas-documents-parser-1 library-parser --check`. A guarantee for every file style cannot be given; this makes the gaps visible on your own files, and every failure class found becomes a test.

## Where read information was lost, and what changed (owner: "how is it being lost?")
Found in the code, fixed:
1. A broken or empty answer from the model was turned into the kind `other` and the document was marked as read for good: empty facts, never retried. Now the model is asked twice; if it still gives nothing usable the document is marked "not understood" (state 3), reported, and tried again every time Read new files is pressed. Nothing is ever called `other` because the model failed.
2. The model was shown only the first 3,500 characters, so totals, due dates and signatures at the end of a document were never seen. It now sees the beginning and the end (3,000 + 1,500 characters), and every amount, date and place is checked against the WHOLE text.
3. Lab values and medicines were read from the first 6,000 characters only; a longer report lost everything after that. A document is now read in overlapping windows of 5,500 characters (up to 12), rows seen twice kept once, each value verified against the window it came from.
4. A party (who a document is from) is kept only when the document contains that name; before, an invented name could stand.
Still true and still visible in the reading report (`unread_files` tool): mail judged not relevant is set aside without the model, and a whole email keeps only its facts.
